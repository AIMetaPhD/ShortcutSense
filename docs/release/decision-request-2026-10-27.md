## 2. 待裁定问题一：是否允许记录内容

### 2.1 Owner 的主张

> 「既然是纯本地和纯本地 AI，记录任何内容都是保护隐私的。这是一个本地软件，也是开源软件，还是一个调用本地 AI 的软件。当然可以记录所有内容，因为所有数据都在它的电脑上。」

### 2.2 正方论据（尽量强的版本）

1. **数据不出机器，是最强的技术隔离。** 没有服务端、没有账号、没有同步，攻击面里不存在「泄露给第三方」这一项。
2. **完全离线 + 开源 = 可审计。** 用户和第三方可以读代码确认没有网络调用，这比任何隐私政策都强。
3. **同类软件的先例。** 剪贴板管理器、本地笔记、屏幕录制工具都保存内容，用户接受，因为价值明确。
4. **当前设计的推断能力确实太弱**（见 §3），弱到无法支撑产品承诺。如果不放宽约束，这个产品可能没有存在理由。
5. **本地 LLM 需要上下文才能有意义。** 现在的 AI 只能拿到几个聚合数字，输出必然是套话。

### 2.3 反方论据

1. **威胁模型不等于「数据外发」。** 同一台 Mac 上任何有 Full Disk Access 的进程都能读这个数据库；Time Machine / 备份盘 / 加密磁盘被挂载后同样；以「~/Documents 或桌面」为同步目录的用户会让数据进入 iCloud/OneDrive。项目自己的 `SECURITY.md` 就写了这一条。
2. **凭据泄露是「种类不同」而非「程度不同」。** 本地键盘记录是 macOS 恶意软件最高价值的单一目标。Keychain 之所以存在，就是因为「本地存密码」本身不可接受。
3. **多人共用设备**：家庭 Mac、公司配发的 Mac、维修送修、二手转卖。用户的输入可能包含别人的数据。
4. **合规**：GDPR 的数据最小化原则；如果用户在办公 Mac 上使用，可能构成对第三方个人数据的未授权处理。
5. **分发成本**：安全软件与商店审核会把「键盘记录器」单独标记。开源可以解释，但解释成本极高，且多数用户不会去读代码。
6. **产品其实不需要它。** 推荐热键、检查冲突、追踪触发次数，这些都不需要知道用户打了什么字。

### 2.4 我的判断

**两边的核心分歧不是「本地安不安全」，而是「本地存储的键盘内容值不值得承担它带来的风险」。**

我的看法：Owner 的论点在**技术层面成立**（数据确实不出机器），但把威胁模型窄化成了「外发」。真实风险里，本地泄露、备份扩散、共用设备、恶意软件四项加起来，权重高于「服务端泄露」——因为我们根本没有服务端。

同时我承认反方第 4 点（推断太弱）是对的：**如果坚持不记录任何内容，这个产品很难立住**。这是一个真实的二难，不是措辞问题。

### 2.5 可选方案（按侵入程度排序）

**方案 A：维持现状（不记录内容）**
- 后果：隐私立场最强，但产品价值最弱。可能需要放弃「消费级应用」定位，转为工程参考实现。

**方案 B：分层同意，默认匿名（我倾向这个）**
- Tier 0（默认）：现状，只存聚合
- Tier 1（显式开启）：存**派生特征而非原文**——例如「同一长字符串重复出现」只存一个本地加盐哈希与次数，用于发现文本扩展机会；原文永不落盘
- Tier 2（显式开启 + 加密 + 保留期）：加密存储内容，密钥在 Keychain，强制 7 天滚动删除，一键清除，排除应用永远不存
- 三层都在设置里明示，切换需要二次确认并解释后果

**方案 C：全面记录（Owner 主张的完整版本）**
- 后果：能做出真正有用的功能（文本扩展、输入效率分析、按内容的智能推荐），但需要重写隐私章节、修改 README 定位、接受分发与合规风险，且与 v2.0 的 AC-05 直接冲突。

**需要回答的问题**：
- Q1. 是否允许把内容写入本地存储？如果是，走 B 还是 C？
- Q2. 如果是 B/C，允许的最小可行字段集合是什么？（需要一个白名单，而不是「什么都行」）
- Q3. 如果只允许 A，产品定位应该怎么改？（见 §3）

## 3. 待裁定问题二：产品价值主张是否成立

### 3.1 事实

当前唯一的核心动作是：**当某应用在 7 天内被激活 ≥7 次、分布在 ≥2 天、且没有明显的键盘导航证据时，建议一个 ⌃⌥⇧+字母 的启动热键。**

这条规则的问题是结构性的：

| 用户类型 | 行为 | 本产品的反应 |
|---|---|---|
| 重度键盘用户 | 已用 ⌘Tab / Spotlight / Raycast 切换 | 被判定「已有键盘路径」，**主动降权，不出推荐** |
| 轻度鼠标用户 | 大量未知来源的切换 | 出推荐——但这类用户会为了一个热键建议去授权输入监控吗？ |

**结果是：最可能受益的人拿不到推荐，最可能装的人收益最小。**

另外三条支柱的实际状态：

- **Learn（学习已有菜单快捷键）**：AX 点击未验证，默认关闭，**等于没有**
- **Configure（引导设置）**：只能给文字指引，不能真的一键
- **周报回流**：显示「用了 12 次」，但没有任何东西让用户下周还想打开

### 3.2 我的判断

**作为消费级应用，这个价值主张目前不成立。** 不是实现不好，是「给谁解决什么问题」这一步没走通。

### 3.3 可选方向

**方向 1：收窄为「新机/新工作流的启动热键设置向导」**
- 面向刚换机、刚装了一堆工具的人，一次性帮他把常用 App 的热键配好
- 优点：诚实、简单、不需要长期采集
- 缺点：低频，装完就走，仍不是「常驻应用」

**方向 2：转向「文本扩展 / 输入效率」**
- 需要方案 B 或 C 的内容记录
- 能回答「你每天重复输入哪些东西」，价值更明确
- 缺点：撞上隐私问题，且与现有推断架构不同

**方向 3：放弃消费级定位，作为「隐私优先的本地推断」工程参考 + 踩坑记录发布**
- 卖点是设计与实测，不是功能
- 我认为这是**当前证据支持的唯一诚实定位**

**方向 4：保留现状，但把 Learn 做通（先做 AX spike）**
- 如果 AX 菜单点击能稳定命中，Learn 这条支柱就活了
- 但需要真机 spike，且 macOS 版本间行为可能不同

**需要回答的问题**：
- Q4. 接受「消费级应用」定位不成立吗？如果不接受，选哪个方向？
- Q5. 是否值得先投入一轮 AX spike（约半天真机验证）来决定方向 4 的可行性？

## 4. 待裁定问题三：本地 AI 层的预期行为

### 4.1 实测到的两个缺陷

**D-035（S2，真实）**：`AppController.explain()` 有完整实现，但**没有任何界面调用它**。
用户打开「启用本地 AI」开关后，界面上不会发生任何事，Ollama 永远不会被请求。
这是「功能声称存在但实际不可达」，属于必须修的类型。

**D-036（S2，真实）**：`OllamaTransport` 硬编码模型名 `qwen2.5:7b`。
Owner 的 Mac 上实际运行的是 `qwen3.5:9b`（`/api/tags` 可查，服务在 127.0.0.1:11434 正常）。
即使接线了，模型名对不上也会失败。

### 4.2 Owner 的期望

> 「如果选择了本地 Ollama，就应该调用本地的 Ollama，而不是让用户去打开监听窗口。」

我理解为：选中本地 AI 之后应当**自动可用**，而不是让用户去配置端点、启动服务、或者在另一个窗口里操作。

### 4.3 需要裁定的边界

「自动可用」有几种实现强度，风险不同：

| 强度 | 行为 | 风险 |
|---|---|---|
| 弱 | 检测 11434 是否可连，不可连时明确提示「未检测到 Ollama」 | 无 |
| 中 | 可连则通过 `/api/tags` **自动选择已安装模型**，不要求用户填模型名 | 无 |
| 强 | 不可连时**自动启动** Ollama | 需要知道安装路径；替用户启动常驻服务是有争议的行为 |
| 更强 | 自动下载/拉取模型 | 消耗用户带宽与磁盘，**不建议** |

**需要回答的问题**：
- Q6. AI 层应该做到哪一档？是否允许应用代替用户启动 Ollama 进程？
- Q7. AI 解释应该出现在哪里——推荐详情页、每周回顾、还是两者都有？

## 5. 缺陷摘要（供审计人判断工程质量）

累计 36 项，全部记录在 `docs/qa/defects.md`。其中我认为**对同类项目有普遍参考价值**的三项：

1. **ad-hoc 签名的指定要求就是 CDHash**。每次重建都等于换了一个应用，用户已授予的 TCC 权限被静默作废。这解释了为什么「授权后一重建就失效」。修法：用固定证书签名。
2. **TCC 按「负责进程」归因**。SSH 启动的进程测到的是 `sshd-keygen-wrapper` 的权限，不是应用的，因此所有远程 GUI 验证的结论都会失效。
3. **CGEventFlags 与 Carbon 修饰位没有任何一位重叠**。混淆后所有快捷键统计静默失效，而按键总数照常上涨，从外部完全看不出来。

这三条在常见 macOS 开发资料里没有集中说明。
